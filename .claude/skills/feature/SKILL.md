# MateHub feature implementation

Цель скилла -- не дать срезать углы. Фича считается сделанной не когда «компилируется», а когда:
- доказано, что она встроена в существующую архитектуру, а не прислонена сбоку;
- она выдержит нагрузку, которую видит остальной код вокруг неё;
- докуменация и тесты приведены в соответствие;
- локальный прогон зеркалит то, что увидит GitHub CI.

Каждый шаг ниже -- gate. Не переходи к следующему, пока предыдущий не закрыт.

---

## 1. Read the map before walking

Прежде чем писать первую строчку:

1. Прочитать релевантные документы в `docs/`. Не «бегло», а целиком соответствующие файлы:
   - `docs/architecture.md` -- общая картина.
   - `docs/project-structure.md` -- где что лежит.
   - `docs/permissions.md` -- если фича касается ACL / ролей / RLS.
   - `docs/chat/`, `docs/video/` -- если фича задевает чат или SFU.
   - `docs/video-service-spec.md`, `docs/str0m-analysis.md` -- если фича в video-сервисе.
   - `CLAUDE.md` (root + `~/.claude/CLAUDE.md`) -- терминология и конвенции.
2. Если документации недостаточно или она противоречит коду -- остановиться и явно сказать пользователю. Не строить на гнилом фундаменте.
3. Записать (в TaskList или в ответ) **список затронутых сервисов** из `services/{common,hub,chat,video,transcoder,general}/` и **затронутые слои фронта** из `frontend/` и `packages/`.

## 2. Read the code you're about to touch

Для каждого затронутого сервиса:

1. Прочитать его `Cargo.toml` (workspace deps) и точку входа.
2. Прочитать модули, к которым фича прилипает. Не «по одному файлу» -- посмотреть, как этот модуль вызывается, кто его вызывает, какие инварианты держит.
3. Найти существующие тесты (`#[tokio::test]`, `tests/` директории) рядом с местом изменения -- они описывают контракт, который нельзя сломать.
4. Если фича пересекает сервисы -- прочитать **обе стороны** интеграции (NATS subjects, REST endpoints, ScyllaDB schemas, WS messages).
5. Frontend: проверить `frontend/components/<feature>/`, `frontend/hooks/`, `packages/sdk-*` если фича доходит до клиента. Перед UI-кодом сверить со списком shadcn-компонентов из `CLAUDE.md` -- свои примитивы не пишем.

Цель: к моменту начала кодирования ты должен уметь объяснить, как фича ляжет в существующую систему, без необходимости что-либо переписывать.

## 3. Implement properly. No quickfixes.

Это самая жёсткая часть скилла. Правило проекта (см. `feedback_no_quickfixes.md` в memory): always choose proper highload architecture over quick hacks.

Разрешено:
- расширять существующие абстракции, если фича действительно требует расширения;
- добавлять новые сущности (актор, NATS subject, таблица), если они оправданы и имеют чёткие границы.

**Запрещено:**
- `unwrap()` / `expect()` на путях, через которые проходит пользовательский трафик. На init -- допустимо с явным сообщением.
- блокирующий I/O в async-контексте. Любая «временная» `std::sync::Mutex` вокруг async-кода -- это будущий инцидент.
- дублирование кода с TODO «потом отрефакторим». Если копируешь -- значит уже есть абстракция, и её надо использовать (или поднять).
- добавление состояния в process-local memory, когда сервис горизонтально масштабируется. Если в Hub'e -- значит в Postgres / Redis / NATS, не в `Arc<Mutex<HashMap>>`.
- N+1 запросы. Любой цикл с `.await` на запрос к БД -- стоп, переписываем на batch.
- мок-структуры в интеграционных тестах для БД, Redis, NATS, Scylla. Тесты обязаны бить в реальный backing store (см. `ci.yml:20-24`).
- silent fallback'и. Если что-то не нашлось -- вернуть структурированную ошибку, а не «как будто и не было».
- `#[allow(...)]` без комментария, объясняющего ровно одну причину.

Backpressure, отмена, таймауты, лимиты на размер payload, идемпотентность для записей -- всё это часть «фича готова», а не «потом добавим».

Принимая нетривиальные решения (выбор схемы данных, формата сообщений, способа инвалидации кэша) -- держи короткий decision log. Он понадобится в шаге 6.

## 4. Tests are part of the feature

Для каждой написанной единицы поведения:

1. Если есть unit-логика без I/O -- юнит-тест в том же файле (`#[cfg(test)] mod tests`).
2. Если фича задевает HTTP / WS / NATS / БД -- интеграционный тест в `services/<svc>/tests/`. Помни про `--test-threads=1` (см. `ci.yml:97-101`) -- не закладывай параллелизм между интеграционными тестами.
3. Frontend: компонент с поведением -- добавить тест туда, где они уже живут. Если их нет -- остановиться и спросить пользователя, добавлять ли инфраструктуру.
4. Покрытие крайних случаев: пустой ввод, отказ зависимости, race на двух конкурентных записях, истёкшая авторизация. Не «happy path и всё».

Не пишем тесты ради coverage. Пишем такие, которые поймают регрессию через 6 месяцев, когда никто уже не помнит контекст.

## 5. Update docs if reality changed

Если фича:
- добавила новый сервис, NATS subject, REST endpoint, WS message, миграцию схемы БД -- обнови соответствующий документ в `docs/`;
- изменила терминологию -- обнови `CLAUDE.md` (root) **и предложи пользователю** как кандидата к коммиту (не правь его молча);
- изменила контракт между сервисами -- обнови оба референса (например, и `docs/chat/...`, и `docs/architecture.md`).

Если документация не нужна -- явно сказать «doc-changes: none, фича не меняет внешний контракт».

## 6. Write down what you changed and why

После того как код и тесты готовы, перед финальным прогоном -- сформировать summary в ответе пользователю:

```
## Что сделано
- (по сервисам / по слоям) -- одна строка на изменение

## Принятые решения
- <решение> -- <альтернатива, которую отклонили> -- <почему>
- ...

## Что я НЕ сделал и почему
- ...

## Риски / следующие шаги
- ...
```

Без этого блока фича не считается сданной. Это не косметика -- это то, что прочитает другой инженер (или ты сам через месяц), когда станет непонятно, почему сделано именно так.

## 7. Run the GitHub CI gate locally. ALL of it. Before claiming done.

Главный источник «вроде всё ок, а MR красный» -- это когда локально запустили `cargo test`, увидели зелёное и решили, что готово. CI завалится на `cargo fmt --check`, на `clippy -D warnings`, на `npm run typecheck` -- и придётся возвращаться, переоткрывать контекст, чинить и пушить заново.

Правило простое: **прогнать локально РОВНО ТЕ ЖЕ команды, что выполняет `.github/workflows/ci.yml`, в той же последовательности, и убедиться, что все они зелёные. До того, как сказать пользователю «готово».**

Источник истины -- `.github/workflows/ci.yml`. Если он изменится -- этот скилл может протухнуть; в таком случае открыть его заново и сверить.

### 7.1. Поднять backing services (ровно те, что поднимает CI services:)

```bash
./scripts/dev-up.sh
```

Поднимает postgres / redis / nats / scylladb (+ minio/turn -- они не нужны CI, но не мешают). Дождаться, пока Scylla примет CQL: CI ждёт TCP до 90 секунд (`ci.yml:81-94`), локально это столько же. Не спешить.

Проверить, что слушают:
```bash
nc -z localhost 5432 && nc -z localhost 6379 && nc -z localhost 4222 && nc -z localhost 9042 && echo "all up"
```

### 7.2. Rust gate -- три команды из `rust-check` job, в порядке как в CI

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all -- --test-threads=1
```

Каждая -- отдельный gate. Если первая упала -- дальше не идём, чиним и начинаем заново с первой.

- `cargo fmt --all -- --check` (`ci.yml:72-73`). Это самый частый source of «MR красный, а локально зелёное». Лечится `cargo fmt --all` (без `--check`), но **запускать ОБЯЗАТЕЛЬНО** именно `--check` после форматирования, чтобы убедиться, что rustfmt сходится в neutral state.
- `cargo clippy --all-targets --all-features -- -D warnings` (`ci.yml:75-76`). `-D warnings` превращает любой warning в ошибку. Не глушить через `#[allow(...)]` без явного однострочного комментария почему.
- `cargo test --all -- --test-threads=1` (`ci.yml:100-101`). Именно `--test-threads=1`. Если тест проходит при `=1` и падает при умолчании (или наоборот) -- значит между интеграционными тестами есть race на TRUNCATE+seed или WS dispatch, и это надо чинить, а не маскировать.

### 7.3. Frontend gate -- ровно команды из `frontend-check` job

```bash
npm ci
npm run lint:frontend
npm run typecheck
```

`npm ci` (а не `npm install`) -- это то, что делает CI (`ci.yml:114`). Лок-файл -- источник истины, никаких локальных install drift'ов.

`npm run typecheck` особенно коварен: он не запускается автоматически при `npm run dev`, и легко уйти в коммит с broken types. Запускать руками.

### 7.4. Final verification

После того как все пять команд (fmt, clippy, cargo test, lint, typecheck) показали зелёное **в одной сессии подряд, без пропусков** -- фича готова к сдаче.

Если хоть одна упала и была починена -- прогнать ещё раз весь набор сначала. fmt мог сломать что-то, что увидит clippy; clippy fix мог сломать тест; и т.д.

### 7.5. Optional: end-to-end smoke поверх CI gate

Это **не** замена и **не** часть CI gate. Это отдельный шаг для UI-фич, которые CI прогнать не может (он не запускает браузер).

Если фича доходит до пользователя через браузер -- поднять полный стек (включая Caddy через `deploy/docker-compose.box.yml`, или просто `npm run dev:frontend` против локально поднятых сервисов) и пройти сценарий руками или через Playwright MCP. CI этого не ловит -- если сломал UX, увидишь только в проде.

Caddy сам по себе CI не «помогает пройти» -- он часть box-деплоя (`deploy/Caddyfile`), а не CI workflow. Не путать локальное end-to-end с CI gate'ом.

### 7.6. После зелёного локального прогона

- сообщить пользователю, что готово, с явным указанием: «прогнал локально всё, что прогоняет `ci.yml`, всё зелёное»;
- предложить commit (не коммитить без явного approve -- см. правила проекта);
- если что-то падает -- **не маскировать**, а чинить корень. Если корень не в скоупе фичи -- остановиться и спросить.

## Anti-patterns, которые надо ловить у себя

- «Сейчас сделаю быстро, потом отрефакторю» -- нет, не отрефакторишь.
- «Тест падает локально, но в CI пройдёт» -- нет, не пройдёт. Чинить.
- «Запустил `cargo test`, всё зелёное -- готово» -- НЕТ. CI это пять gate'ов: fmt, clippy, cargo test, npm lint, npm typecheck. Запускать **все пять** локально, иначе MR ляжет на форматтере или на typecheck, и придётся переоткрывать контекст и пушить заново.
- «Я форматнул через IDE, наверное всё ок» -- не «наверное», а проверить через `cargo fmt --all -- --check`. IDE-форматтер и rustfmt-в-CI -- разные сущности.
- «Clippy предупреждает, но не ошибка, проигнорирую» -- в CI стоит `-D warnings`. Любой warning -- это будущий красный MR.
- «Это edge case, маловероятно» -- highload-сервис видит edge cases каждые 10 секунд.
- «Я обновлю доки в следующем PR» -- не обновишь.
- «Добавлю allow(dead_code) пока что» -- если код dead, удали. Если не dead, используй.
- «Этот mock проще чем поднимать настоящий Postgres» -- интеграционные тесты ходят в реальный store, точка (см. `ci.yml:20-24`).

## Когда остановиться и спросить

- противоречие между докой и кодом;
- фича требует изменения схемы БД с потенциальной миграцией прод-данных;
- фича добавляет новую внешнюю зависимость (crate / npm package);
- фича требует нового сервиса или нового NATS subject верхнего уровня;
- неясно, в каком сервисе должна жить логика;
- падает существующий тест, и непонятно, регрессия это или фича его честно обесценила.

В этих случаях -- стоп, summary текущего состояния пользователю, ждать решения.
